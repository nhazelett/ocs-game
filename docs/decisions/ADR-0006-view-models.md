## Title
ADR-0006: View-model contracts for the morning board and the two editors

## Status (Proposed / Accepted / Superseded)
Accepted

## Context
Backlog M0-07. The Godot desk (M1-05, then M2) needs a stable shape for what it shows: the top strip, the morning board, the requirement editor (OCS seat) and the action editor (CCO seat). SPEC section 2 makes the action editor's hard-stop versus soft-gap display one of the first UI experiments, so the editor has to be able to ask "what would this award do" without doing it. ADR-0005 already fixes that the Game reads through `SessionView` and changes state only through `Apply` and `AdvanceDay`.

## Options considered
1. The Game reads raw state (`Arrangements`, `Work`, `Records`) and works the board and editor logic out itself.
2. Interfaces in the Sim that the Game implements or mocks.
3. Immutable snapshot records built by the Sim on request, plus a side-effect-free `Preview` for awards.

## Decision
Option 3. Namespace `LinesOfSupport.Sim.Views` (`src/LinesOfSupport.Sim/Views/ViewModels.cs`), built from `SessionView`:

- `TopStrip()` -> `TopStripView`: day, shop hours per day, hours queued and queue days, cash and its full value, replenish day, usable funds, system-online, paying agent, GPC.
- `MorningBoard()` -> `MorningBoardView`: the records written by the last `AdvanceDay`, classified into `BoardCategory` (Delivery, Failure, Report, Request, VendorNotice, HigherHq, Event) and `BoardSeverity` (Alert first), each with a `BoardLinkKind` and link id (arrangement, card, `site.capability`, island, event, cash, work) and its `CausedBy` chain; plus one `CapabilityTile` per site capability. The player's own actions and rejections are not board items.
- `RequirementEditor(cardId)` -> `RequirementEditorView`: the card, peak demand over its window, each line with its kind and the consequence of leaving it off, each dependency with coverage `inRequirement`, `arranged` or `none`.
- `ActionEditor(siteId, capabilityId, cardId?)` -> `ActionEditorView`: instruments with the fact that blocks each one today, per-action limit, shop hours and start lag; vendors offering the capability with free capacity, lead time, quoted unit price and mobilization; known vehicles; funding lines.
- `Preview(AwardAction)` -> `ActionPreview`: the exact hard stops `Apply` would return (same code path, `Session.CheckAward`), soft gaps the sim will play out, daily cost, mobilization, total, shop-hour range and earliest-start range at best and worst roll ignoring the queue ahead.

Records rather than interfaces: the Game binds to data, and records are trivially faked in Godot-side tests by constructing them. Building any view changes nothing and draws no random number; a test plays the textbook policy with every view built twice a day and requires the same state hash as a plain run.

Text in views states facts and limits ("No operators line: daily failure odds rise while it runs"), never directions on how to do the job.

## Consequences
- Codex binds the M1-05 shell's top strip to `TopStrip()` and M2's panels to these views instead of raw state.
- Adding a field, a category or a link kind is additive. Renaming or removing one is a new ADR.
- Quotes are the scenario's offer prices until the quote band and market research land (assumptions.md, Pricing); `UnitPriceCents` keeps its name and meaning when they do.
- The instrument list shows only instruments implemented in this build; IDIQ and others appear with their milestone.

## Addendum, 2026-11-08 (M2-08): debrief view
`SessionView.Debrief()` -> `DebriefView` (`Views/DebriefViews.cs`): capability bands by day (-1 before a site opens), timeline events, decisions with each island's information tier at the time, gaps (consecutive days below 100% per site capability) each tagged `Avoidable`, `Discoverable` or `Unforeseeable` (SPEC 4) from its factors, scorecard, and commitments. A gap takes its most controllable factor's tag; a `Dependency` factor inherits the tag of the gap it points to. The builder diagnoses from end-of-game state (arrangement dates and lines, survey records, population, records by day) and is read-only, so it is safe mid-game. Tag rules per factor are in docs/assumptions.md (Debrief tags). The text report gains a GAP TAGS section built from it.

## Addendum, 2026-11-08 (M2-09): prep screen
`PrepScreen.View(bundle)` -> `PrepView` (budget days, the cost of all choices together, and each choice with what it changes "with" and "without", flagging choices this build records but does not model) and `PrepScreen.Check(bundle, picks)` -> `PrepCheck` (accepted, days used, stops). Both work before a Session exists; the game shows the prep screen, then calls `Session.Create(bundle, seed, picks)`. Check's stops are the same messages Create throws. Create now also rejects a choice picked twice.

## Addendum, 2026-11-08 (Q11): per-arrangement ledger field
`Arrangement.UnobligatedIncurredCents` (read-only): incurred minus obligated, clamped at zero, and always zero for a coordination arrangement. The metric `cost.unobligatedIncurredCents` is now computed as the sum of this property, so the ledger row and the total cannot drift. The game's Ledger panel (M2-05) reads it from `SessionView.Arrangements` and does no arithmetic of its own.

## Addendum, 2026-11-08 (M2-14): commander confidence
`SessionView.LostConfidenceSites` (sites whose commander lost confidence through a refused handshake) and a new `GapFactorKind.PriorityDeferred` (appended; Avoidable). The rule itself is in docs/assumptions.md (Commander priority when capacity is short). The held-back record is a `RecordKind.Compliance` record whose subject is the work item id. Additive; no existing view changes shape.

## Addendum, 2026-11-08 (M2-19): seeded disruptions
`SessionView.PlannedPopulation(siteId, day)` (the scenario plan's population; `Population` now includes unplanned arrivals once their notice has come) and a new `GapFactorKind.PopulationJump` (appended; Unforeseeable for 7 days after the arrival, then Avoidable). The arrival notice is a `RecordKind.Event` record whose subject is the site id; a ferry forecast is a `RecordKind.Knowledge` record whose subject is the event id (`ferryWeather`), so the morning board links it as an Event. Scenario schema additions (Fable lane): effect `daysRange` and `forecastDays`, effect kind `site.populationJump`, vendor offer `sourceIsland`. Additive; no existing view changes shape.

## Addendum, 2026-11-08 (M3-02): counterfactual view
`Counterfactual.Choices(session)` lists every logged action by its index in the input log, with its day, kind, text and whether it was rejected (`Session.AppliedRejected`, parallel to `AppliedActions`). `Counterfactual.Run(bundle, log, change)` applies one `CounterfactualChange` (Replace an action, Remove it, Insert one on a day, after that day's actions or before a given one, or SetPrep) and re-runs both logs with the same seed, from day 1 (identical up to the change's day, so this is the same as re-running from that day, and costs about 20 ms for 90 days). `CounterfactualView`: FromDay, HorizonDay (the last day for a finished game; the last day played for a mid-game save), ChangeText, both scorecards, MissionOutputDelta, `GapDiff` per gap (Gone, Shrunk, Unchanged, Worse, New, by shortfall in permille-days over the gap's days, with down days and both gap indexes) and `NoLongerApplied` (actions the re-run refused that the played game did not). NoLongerApplied exists because one changed decision often moves later ones: in the SPEC 5 example, adding the hub fuel coordination removes the day 10 outage, so the day 11 handshake never happens and the logged ratification of it is refused. The re-run replays the rest of the log as logged; it does not ask a policy what the player would have done instead.

## Addendum, 2026-11-08 (M3-03): funding in the views
`FundingOption` gains optional trailing fields `PlannedAvailableDay`, `Capabilities` and `PaysForThis` (whether the line's purpose covers the action editor's capability); a later `AvailableDay` than `PlannedAvailableDay` is a late release. `BoardLinkKind.Funding` (appended): `LinkId` is a funding line id, or `funding` for the shop's money as a whole; open the ledger. `RecordKind.Funding` items show on the morning board as Report: Info for a release, Warning otherwise, and appear on the debrief timeline. `GapFactorKind.FundingLapse` (appended): nothing supplied the capability on a day with no line able to pay for it; Avoidable when money was usable before the window, Unforeseeable when none had been released (docs/assumptions.md, Debrief tags).

## Addendum, 2026-11-08 (M3-04): CORs in the views
`SessionView.CorModeled`, `SessionView.Cors`, `SessionView.CorSummary(cor)` ("fair: reports 2 day(s) late, about 80% of problems") and `SessionView.CorQuality(cor)`. `SessionView.Known(record)` is false for a `VendorFailure` record the office has not been told about; any record list shown to the player filters on it (the morning board already does). `RecordKind.CorReport` items show on the morning board as Report / Warning; `LinkKind` is Arrangement for a failure report and None for the rotation notice (its subject is the COR id). `Preview(award)` adds a soft gap for a written award with no COR ("No COR named: ...") or with a COR worse than good ("COR SGT Okafor is fair: ..."). Debrief VendorFailure factors say how the office heard: same day, the day the COR reported, the day the unit reported after the mission effect, or never.

## Addendum, 2026-11-08 (M3-05): external support in the views
`SessionView.PreviewExternalSupport(request)` returns an `ActionPreview`: the same hard stops `Apply` would give, soft gaps (approval and mobilization ranges with the earliest arrival day, a `supplies` line left off, quantity below peak demand, start later than the card asks, the line needing the money at award, the COR gap), the estimated daily, mobilization and total cost, shop hours, and in `EarliestStartMin/Max` the first day of performance at the best and worst rolls, ignoring the queue. `SessionView.ExternalSupportRequests()` lists `ExternalSupportRequestView` rows: status (`Preparing`, `InApproval`, `Awarded`, `Refused`), requested and submitted days, the expected answer range (submitted + rules approval min and max; the drawn day is not shown), awarded, start and end days once awarded, quantity, total, funding line, card and the refusal reason. `SessionView.ExternalSupport` is the scenario's provider data (null when there is none). `RecordKind.ExternalSupport` items show on the morning board as HigherHq / Info, linking to the work item before award and to the arrangement after. The CCO action editor does not list `externalSupport`: it is the OCS seat's request, not a CCO instrument. The OCS seat screen that binds these waits for the M2 gate (FOR-NICK #3).

## Addendum, 2026-11-08 (M3-06): ACSA in the views
`SessionView.PreviewAcsa(order)` returns an `ActionPreview` (hard stops as `Apply`; soft gaps for withdrawability, supply lines not included, quantity below peak, a late start against the card, an off-island partner; reimbursable daily and total cost; shop hours; first day of support at the best and worst roll). `SessionView.AcsaPartner` is the partner data (null when none is present); `SessionView.AcsaWithdrawn` lists withdrawn capabilities ("*" for all). Withdrawals arrive as `RecordKind.Withdrawal` linking to the arrangement. The action editor does not list `acsa`; an ACSA order is its own action, and its screen (or a Directory row for the partner) is Codex's call within the existing screens, or waits for the gate if it needs a new one.


## Addendum, 2026-11-08 (M3-06): host nation support in the views
`SessionView.PreviewHostNation(request)` returns an `ActionPreview` (hard stops as `Apply`; soft gaps for withdrawability, supply lines not included, quantity below peak, a late start against the card, an off-island source; cost share daily and total, zero when the host nation bears it; shop hours; first day of support at the best and worst roll). `SessionView.HostNation` is the agreement or null; `SessionView.HostNationWithdrawn` lists withdrawn capabilities ("*" for all). Debrief factor `HostNationWithdrawn`. No game screen yet: a request form waits for the M2 gate like the other new route forms.

## Addendum, 2026-11-08 (M3-06): off-island sourcing in the views
`SessionView.Preview(award)` with an off-island vendor and `Lift` adds the lift to the start range (best case: queue or transit minimum; worst case: maximum plus every bump and the longest customs hold) and a soft gap naming the mode, its days, bumping (airlift) and customs. `VendorData.Lift` and `VendorData.OffIsland` let the action editor offer a lift picker for off-island vendors; that picker is a change to the action editor and waits for the M2 gate. Debrief factor `LiftDelay`.

## Addendum, 2026-11-08 (M3-05): the transition planner's view
`SessionView.Transitions()` returns a `TransitionView` per plan: both arrangements' days, the outgoing's planned last day, the incoming's start (known, or the projected min and max for an external request not yet awarded), whether the incoming is lost, projected gap days at the earliest start, full days and days both running so far, status (`planned`, `overlapping`, `cuttingOver`, `clean`, `gap`) and `Warnings` (soft gaps: a coverage gap certain or possible, an outgoing that ends before the overlap can be verified, less overlap than planned before an `onDay` cut-over, the incoming below peak demand after the cut-over, and for a pending external request a funding line that expires before the award or is short of its total). `SessionView.PreviewTransition(plan)` returns a `TransitionPreview` (hard stops as `Apply`, soft gaps, the projected `TransitionView`); it changes nothing. `RecordKind.Transition` shows on the morning board as Delivery / Warning linking to the outgoing arrangement, and on the debrief timeline. Debrief factor `TransitionGap` (tag rule in docs/assumptions.md). The report gains a TRANSITIONS section when plans exist. The transition planner screen (overlap bars) is new UI and waits for the M2 gate.

## Addendum, 2026-11-08 (M3-17): hidden inherited problems and the file review
Inherited rows with `visibleProblem: false` gate what the views show; the state stays true. `SessionView.ProblemHidden(arrangement)` is true until the problem is found; while it is, the game shows the row as an ordinary contract: not its `Uca` (clocks, overdue, proposal), `SessionView.ShownReliabilityPermille(arrangement)` rather than `ReliabilityPermille`, and for an IDIQ order no ceiling or ordered value (`SessionView.IdiqTermsHidden(vehicleId)`; `ActionEditor` already nulls `VehicleOption.CeilingCents`, `OrderedCents` and `GuaranteeUnorderedCents`, and `SessionView.Idiqs` should be read through it). `SessionView.Known(record)` now also returns false for a hidden UCA's `UcaOverdue` and `UcaProposal` records; the morning board leaves them out. Known is as of today, so a record can become known once found.
`ReviewFilesAction` (`kind: "reviewFiles"`, optional `arrangements`; empty means every unreviewed inherited contract file) is shop work at rules `fileReview.hoursPerArrangement` per file. `SessionView.PreviewReviewFiles(review)` gives its stops, hours and the day findings would come in; `SessionView.InheritedFiles()` lists the reviewable files (`InheritedFileView`: arrangement, site, capability, instrument, reviewed day, in review, findings record). When the work is done each file yields a `Knowledge` record with the arrangement as its subject (board link `Arrangement`). A `Compliance` inquiry on a hidden past-due UCA also reveals it. Debrief: a vendor failure on an overstated inherited record and a stop-work on a hidden inherited UCA are Discoverable while unfound on the day and Avoidable once found (docs/assumptions.md, Debrief tags). The textbook policy reviews every file on day 1 when there are any; greedy and do-nothing never do.

## Addendum, 2026-11-08 (M3-19): claims in the debrief
`ScorecardView` gains trailing `Claims` and `ClaimCents`; `DebriefView` gains trailing `Claims` (`ClaimLine`: arrangement, filed day, amount, settled day, filing text). Both default so existing constructions compile. The action editor's terminate control offers "with N days' notice" when `Arrangement.NoticeDays` is set; the ledger lists `SessionView.Claims`.

## Addendum, 2026-11-09 (M2R-01): people in the views
Scenario data gains `people[]` (id, name, rank, unit, role, optional portrait key, vendor, site, and `lines` keyed by moment). Requirement cards name a `person` (and carry their `message`); free-text `submittedBy` remains only for a card with no person. `actors.sco`, `actors.fm` and `actors.commander` name a person; events may name who the player hears them `from`. The bundle refuses unknown references, a wrong role on an actor, a vendorRep with no vendor and duplicate ids.
`PersonView` is what the game shows: `DisplayName` ("Capt Ana Ruiz"), `WithUnit` ("Capt Ana Ruiz, 3 CES"), `Line(moment)`, `VendorName` for a vendor's rep. `Id` is for lookups and never goes on screen. `BoardItem` gains trailing `Person` (the card's person, the event's speaker, or the arrangement vendor's rep; null for no one in particular). `RequirementEditorView` gains trailing `Title` ("Power for Spoke B"), `Person` and `Message`, and its `SubmittedBy` is the person's `WithUnit` when there is one. `SessionView` adds `People`, `Person(id)`, `CardPerson(card)`, `CardTitle(card)`, `CommitmentPerson(commitment)` (the vendor's rep), `RecordPerson(record)` (same rule as the board), and `ScoContact`, `FinanceContact`, `Commander`, `OutgoingCco`. All new parameters default, so existing constructions compile. None of this is in the state hash; every golden is unchanged.
Not in this addendum: record, hard-stop and debrief text still names arrangements, cards and funding lines by id in places ("Ratification of uc1 ... from om1"). Replacing those with names is M2R-07.

## Addendum, 2026-11-09 (M2R-02): the turnover and the prep message
Scenario data gains `briefing` (title, situation, due), `turnover` (from: the outgoing CCO; a remark opening each of the shop, contracts, vendorList and money paragraphs; per-item `remarks` keyed by inherited arrangement, vendor and funding line) and `prepBriefing` (from, intro, a line per prep choice, `defaults` that must fit the prep budget). The bundle refuses a `turnover.from` who is not an outgoingCco, an unknown prep choice and defaults over budget; a remark for an item that is absent is ignored (derived fixtures strip items), and validate.py flags it for authors.
`SessionView.Turnover()` returns a `TurnoverView`: `From`, `Greeting` and `LastLine` (the outgoing CCO's `greeting` and `farewell` lines), `Briefing`, four `Sections` (Shop, Contracts, Vendors, Money) whose `Text` is one prose paragraph each (R9: no bullets, headers or ids), and the same facts as rows (`TurnoverContract`, `TurnoverVendor` with the vendor's information tier as `Confidence`, `TurnoverMoney`). The shop paragraph reads the shop as prep left it. Contracts are listed from the handover rows and name no instrument, clock or reliability, so a hidden problem (M3-17) never reaches the turnover; remarks are what the outgoing CCO believes. A scenario without turnover data still gets the four paragraphs of facts. `PrepView` gains trailing `From`, `Intro` and `Defaults`; `PrepOption` gains `Says` and `Default`. Nothing here is in the state hash.
