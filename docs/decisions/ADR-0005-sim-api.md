## Title
ADR-0005: Simulation API for the Harness and the Game

## Status (Proposed / Accepted / Superseded)
Accepted

## Context
Codex asked (Q5) for a harness-facing contract: load, seed, advance, apply dated actions, policies, metrics. The Godot desk will bind to the same surface. The shape below is what M0-05 implemented; it replaces the sketch in the Q5 answer where they differ.

## Options considered
1. Expose the mutable session to callers.
2. Session mutates only through `Apply` and `AdvanceDay`; callers read through a read-only `SessionView`, flat metrics and cause records.

## Decision
Option 2. Namespace `LinesOfSupport.Sim`:

- `ScenarioBundle.Load(scenarioDir, rulesDir = null)`: reads `scenario.json` and `scenarios/rules/rules-<rulesVersion>.json`; checks references and that every event, effect and prep kind is implemented.
- `Session.Create(bundle, seed, prepChoices = null)`; `session.Day` (day about to be played, from 1), `LastDay`, `Finished`.
- `session.Apply(PlayerAction) -> ActionResult` (Accepted, Message, HardStops). Actions: `survey`, `setLine`, `award` (instruments sf44, gpc, purchaseOrder, bpaCall, uca in M0), `coordinate`, `definitize`, `terminate`. Rejections change nothing except a `Rejected` record.
- `session.AdvanceDay()`.
- Read surface: `session.View` (`SessionView`), `session.Metrics` (flat `IReadOnlyDictionary<string,double>`, keys match `passCriteria.metric`), `session.Records` (`CauseRecord` with `CausedBy` ids), `session.StateHash()`.
- Saves and replays: `InputLog` (JSON: scenario, rulesVersion, seed, prepChoices, actions with `kind` first and `day`); `Replay.Run(bundle, log)`; `Replay.Run(bundle, seed, policy)`; `session.ToInputLog()`.
- Policies: `IPolicy { Name; PrepChoices(bundle); Decide(SessionView) }`; `PolicyCatalog.Create("do-nothing" | "greedy" | "textbook")`.
- Text report: `SessionReport.ToText(session, title)` (timeline, capability-by-day strip, scorecard, gap chains, pass criteria, hash).

## Consequences
- The Harness swaps `PlaceholderRun` for `Replay.Run` and prints `SessionReport.ToText` (backlog M1-01, Codex).
- The Game binds its panels to `SessionView` and records; it never mutates state except through `Apply`/`AdvanceDay`.
- Adding an action kind or a metric key is additive; renaming one is an ADR.

## Addendum, 2026-11-08 (M2-12): establishBpa
Action `establishBpa { id, vendor, capability, scopeLines, callLimitCents?, orderingPeriodDays? }` (additive). Costs `bpaEstablish` shop days at today's manual or system speed; on completion the BPA joins `SessionView.Vehicles` (scenario vehicles plus established ones) and takes `bpaCall` awards with the existing checks and decline odds. Call limit defaults to the simplified acquisition threshold and may not exceed it; ordering period defaults to the rest of the scenario. `SessionView.PreviewEstablish(action)` returns hard stops, shop hours and the first day calls could be placed.

## Addendum, 2026-11-08 (M2-18): cureNotice and performance issues
A contract with written terms awarded by this office that under-delivers on `performance.underDeliveryDays` of the last `windowDays` days opens a performance issue (`SessionView.PerformanceIssues`, Inbox record). Action `cureNotice { issue }` (additive) costs `cureNoticeShopHours`; when delivered, a `cureDays` cure period starts, and at its end a roll on the new `performance` stream (`cureRecoverPermille`) decides cured (reliability raised to `curedReliabilityPermille`) or default (reliability drops by `defaultReliabilityDropPermille`). Re-source and terminate use the existing award and terminate actions; `SessionView.PerformanceDecision(issue)` reads the choice back for the debrief. New rules block `performance` (rules schema). Metrics `performance.issues`, `cureNotices`, `cured`, `defaults`. Textbook issues a cure notice the morning an issue arrives.

## Addendum, 2026-11-08 (M3-01): saves and resume
A save is an `InputLog` with `savedDay` (additive, optional): the day about to be played, with every action dated that day already applied and the day not advanced. `session.ToSave()` writes it (`savedDay` absent once the game is finished); `Replay.Resume(bundle, log)` replays days before `savedDay`, applies that day's actions in log order and returns the session on that day. A log without `savedDay` plays to the end as before, so every existing input log and golden is a valid save. Resume refuses a log for another scenario or rules version, a `savedDay` outside the scenario's days, or an action dated after `savedDay`. No state snapshot is stored: replay is the only load path, so a save can never disagree with the rules (SPEC 8); a snapshot for quick resume can be added later as a cache checked against `StateHash()`. The game autosaves `ToSave()` each morning after the day advances and on demand (M3-08, Codex).

## Addendum, 2026-11-08 (M3-06): establishIdiq, idiqOrder and the capacity event
Action `establishIdiq { id, vendor, capability, scopeLines, ceilingCents, minimumGuaranteeCents?, orderingPeriodDays?, fundingLine }` (additive). Single award. Costs `idiqEstablish` shop days (8 to 15) at today's manual or system speed. The minimum guarantee defaults to, and may not be below, `idiqEstablish.obligatesMinimumGuaranteeFraction` of the ceiling (5%), may not exceed the ceiling, and is obligated from `fundingLine` when the work completes (refused with a Rejected record if the line can no longer cover it). The ceiling may not exceed the warrant. On completion the IDIQ joins `SessionView.Vehicles` (kind `idiq`, `ceilingCents`) and `SessionView.Idiqs` (`IdiqState`: ceiling, ordered, guarantee not yet ordered). `SessionView.PreviewEstablish(EstablishIdiqAction)` returns hard stops, shop hours, the guarantee in `TotalCents` and the first day orders could be placed.

`award` with `instrument: "idiqOrder"` and `vehicle` orders against it: hard stops outside scope, past the ordering period, over the ceiling (counting orders still in shop work), wrong vendor or place of performance. Binding: orders are never declined, and they are not stopped at the vendor's capacity. An order spends the guarantee not yet ordered first (`Arrangement.FromGuaranteeCents`) and new money from `fundingLine` for the rest; a fully guarantee-funded order needs no funding line. Terminating an order never returns its guarantee-funded part. `cost.obligatedCents` adds the guarantee not yet ordered: it is owed whether or not it is ordered.

Capacity event: each day, for a vendor and capability with an IDIQ order running, if running arrangements exceed the offer's `capacityPerDay`, other instruments' arrangements (inside capacity when awarded) are served first and IDIQ orders share the rest oldest first; an order short of its quantity delivers the fraction it gets. New `RecordKind.VendorCapacity` (one record per episode, a cause of the shortfall), debrief factor `GapFactorKind.VendorCapacity` (avoidable: the order preview showed the capacity left). Not a performance issue: no `VendorFailure` record. No random draws, and games without IDIQ orders are unchanged (all goldens identical). `VehicleOption` gains optional `CeilingCents`, `OrderedCents`, `GuaranteeUnorderedCents`; the action editor lists `idiqOrder`, greyed until an IDIQ is open.

## Addendum, 2026-11-08 (M3-03): funding lines, purpose and a late release
Scenario `fundingLines[].capabilities` (optional; absent or empty means any) is the line's purpose. `FundingLineState` gains `PlannedAvailableDay`, `Capabilities` and `Pays(capability)`; `AvailableDay` gets an internal setter (still read-only outside the Sim). The scenario field `replacementArrivesDay` is removed (it was never read); a replacement is a second line whose release a scenario event can delay. New event effect `funding.late { target: line id, days | daysRange }`: the comptroller pushes the line's release back; it does nothing once the line is released. New hard stops (editor and `Apply`): a line whose purpose does not cover the capability (awards, `establishIdiq`, `definitize`); a severable service longer than `Session.SeverableServiceMaxDays` (365) that runs past its line's year end. Ratifications choose only a line whose purpose fits. An award rejected at completion for money now says why (expired, not released, or short). New `RecordKind.Funding` (appended), written at the end of each day for the next morning: a release, a late notice, the warning `Session.FundingExpiryWarningDays` (10) before a year end with money unobligated, the expiry, and the first day no line has money usable. No new random draws in existing streams: the delay is drawn from the events stream at creation, after the other events, so scenarios without the event replay unchanged.

## Addendum, 2026-11-08 (M3-04): CORs and report fidelity
Scenario `cors[]` (`id`, `name`, optional `unit`, `quality`) is the COR roster; rules `cor` gives `qualities` (`lagDays`, `reportPermille`), `noCorLagDays` and `reliefQuality`. A scenario without a roster behaves exactly as before. `AwardAction.Cor` (optional) designates a COR at award; a COR on an instrument without written terms, an unknown COR or a COR in a scenario without a roster is a hard stop. New `DesignateCorAction { Arrangement, Cor }` (`kind: "designateCor"`) designates or replaces the COR on a running or pending contract this office awarded with written terms; it takes effect at once, with no shop hours. `Arrangement.CorId` holds the designation. `Session.Cors` (`CorState`: `Id`, `Name`, `Unit`, `Quality`, `RotatedDay`), `Session.CorReports` (`CorReport`: arrangement, failure day, arrive day, COR or null for a unit report, the failure record, and the delivered record) and `Session.CorModeled` are read-only.

With a roster, a vendor failure on such a contract is reported, not seen: the COR's quality sets the lag and the odds (one draw per failure from a new "cor" stream, none at 100%, so other streams never shift); with no COR the unit reports a failure only when the site's capability was below full that day, `noCorLagDays` later. New `RecordKind.CorReport` carries reports and the rotation notice. Performance issues on these contracts open from reported failure days (same two-in-three rule), the issue text names the source, and its causes include the reports and the failures. Event effect `cor.rotates` (target: COR id) turns the COR into an untrained relief at `reliefQuality`; the designations stay. The textbook policy names the best COR on every written award and re-designates when a relief is worse than someone else on the roster; greedy names none.

## Addendum, 2026-11-08 (M3-05): requestExternalSupport
New `RequestExternalSupportAction { Id, Card | Site + Capability, Lines?, Quantity, StartDay?, DurationDays, FundingLine, Cor? }` (`kind: "requestExternalSupport"`), the OCS seat's support request (SPEC 4.1, SPEC 5 approach 4). The provider is scenario data: optional `actors.externalSupport { provider, offers[] { capability, lines, capacityPerDay, unitPriceCents, mobilizationFraction, reliability, sites } }`; a scenario without it refuses every request. Rules `instruments.externalSupport` supplies `shopDays`, `approvalLagDays`, `mobilizationDays` and `minimumUsefulDurationDays` (already in rules 2025-10).

Hard stops: no provider or no offer for the capability or site; a line the offer lacks; scope missing a core, operator or maintenance line the offer has (self-managed); quantity above the offer's capacity less other live requests; duration under the minimum; funding line missing, not usable today, short of the estimated total, or failing the purpose and 12-month checks; a COR as for awards. Accepted, the request draws its shop days, approval lag and mobilization at once from a new "external" stream (no other stream shifts), queues a `WorkKind.ExternalSupportRequest` item after the FM certification lag, and on completion is submitted (`ExternalSupportStatus.InApproval`). On submitted day + lag, after shop work and before the lifecycle step, the external office awards: the whole task order (unit price x quantity x duration, plus mobilization) is obligated from the line and the arrangement with the request's id is created (instrument `externalSupport`, no vendor id, supplied on the site's island, `supplies` lines sized as for awards), starting the later of `StartDay` and award + 1 + mobilization. If the line can no longer pay, the request is `Refused` and the debrief's funding factor sees it. New `RecordKind.ExternalSupport` for submission, award and refusal. Payment errors do not apply (not a manual local contract); vendor failures, performance issues and COR reporting do. The debrief's uncovered-gap text explains an external contract that started after the gap. Goldens: spoke-b-90 `approach4-external-only`, `approach4-external-with-uca-bridge`.

## Addendum, 2026-11-08 (M3-06): acsaOrder and acsa.withdraw
New `AcsaOrderAction { Id, Card | Site + Capability, Quantity, StartDay?, DurationDays, FundingLine }` (`kind: "acsaOrder"`). Scenario `actors.acsaPartner` gains optional `name`, `island`, `unitPriceCents` (capability to price per unit-day) and `reliability`; `stock` is units per day the partner can spare. Hard stops: no partner present, no stock for the capability, a withdrawn capability, quantity above stock less other orders on overlapping days, and the usual funding checks. Accepted, the order draws its shop days and start lag from a new "acsa" stream, queues `WorkKind.AcsaOrder` after the FM certification lag, and on completion obligates the reimbursement in full and creates the arrangement (instrument `acsa`, no vendor id, lines = the capability's non-supply lines, supplied from the partner's island or the site's). New event effect `acsa.withdraw` (target capability or absent for all; `days`/`daysRange` notice) ends running orders at the notice, returns unperformed reimbursement to a current line, and stops new orders. ACSA arrangements take no cure notice or COR. New `GapFactorKind.AcsaWithdrawn`. No shipped scenario has a partner yet, so no golden moves; M3-07 uses it.


## Addendum, 2026-11-08 (M3-06): hostNationRequest and hostNation.withdraw
New `HostNationRequestAction { Id, Card | Site + Capability, Quantity, StartDay?, DurationDays, FundingLine? }` (`kind: "hostNationRequest"`). Scenario `actors.hostNation` gains optional `name`, `island`, `capacity` (capability to units per day the agreement provides), `unitPriceCents` (the shop's cost share per unit-day) and `sites` (empty: all). Hard stops: no agreement, a capability with no capacity, a site not covered, a withdrawn capability, quantity above capacity less other requests on overlapping days (inherited host-nation arrangements do not count against it), and the usual funding checks when there is a cost share. With no cost share no funding line is needed and the work does not wait for FM certification. Accepted, the request draws shop days and start lag from a new "hostNation" stream, queues `WorkKind.HostNationRequest`, and on completion obligates any cost share and creates the arrangement (instrument `hostNation`, no vendor id, lines = the capability's non-supply lines). New event effect `hostNation.withdraw` (target capability or absent for all; `days`/`daysRange` notice, else drawn from rules `hostNation.withdrawalNoticeDays`) ends every running `hostNation` arrangement for it, inherited ones included, returns unperformed cost share to a current line, and stops new requests. New `GapFactorKind.HostNationWithdrawn` (Avoidable for a request, Discoverable for inherited support). No shipped scenario has an agreement block or the event, so no golden moves.

## Addendum, 2026-11-08 (M3-06): off-island sourcing
`AwardAction` gains optional `Lift` ("airlift" or "sealift"). Scenario vendors gain optional `lift` (modes they ship by); a vendor with any is off-island and its `island` is the port of entry. Rules gain `lift` (airlift queue, bump chance, bump delay, max bumps, sealift transit, customs hold chance and days). Hard stops: an off-island vendor without a lift mode or with one it does not offer, airlift for a consumable capability, an SF 44 to an off-island vendor, and a lift mode on a local vendor. The transit days are drawn from a new "lift" stream when the award is applied (after the existing work-stream draw, so local awards replay unchanged) and added to the offer's lead time. Each off-island arrangement gets a shipment record; on its due day `Lifecycle` rolls an airlift bump, then one customs hold, each moving `StartDay` and `EndDay` later. New `GapFactorKind.LiftDelay` (Unforeseeable). No shipped scenario has an off-island vendor, so no golden moves.

## Addendum, 2026-11-08 (M3-05): planTransition
New `PlanTransitionAction { Id, Outgoing, Incoming, OverlapDays?, Handoff?, CutoverDay?, Owner? }` (`kind: "planTransition"`). Incoming is an arrangement or an external support request id (the arrangement it becomes keeps the id). `Handoff` is `"incomingDelivering"` (default) or `"onDay"` with `CutoverDay`; `OverlapDays` defaults to rules `transition.defaultOverlapDays`; `Owner` is `"cco"` (default) or `"ocs"`. Rules gain an optional `transition` block (`defaultOverlapDays`, `warnDays`). Hard stops: missing or reused id, an outgoing that is not a running arrangement, an incoming that is neither a running arrangement nor a request that has not been refused, the same id on both sides, a different site or capability, an outgoing already in an open plan, an overlap under one day, an unknown handoff or owner, and for `onDay` a missing cut-over day, one not after today, or one after the outgoing ends. Planning costs no shop hours and draws no random number. Each day after supply is resolved (and after COR reporting, before money), `TransitionClocks` counts the incoming's consecutive full days (factor 1000, no failure, no capacity shortfall, not stopped), starts a `WorkKind.Terminate` item for the outgoing when the handoff condition is met (an ordinary termination with its shop hours, so its last day is the next day when the shop has the hours), records a `RecordKind.Transition` warning once when the outgoing ends within `warnDays` and the incoming is lost or projected to start after it, and resolves the plan the day after the outgoing's last day: `Clean` when the incoming is running that day, `Gap` otherwise. `Session.Transitions` lists `TransitionState`. Metrics `transitions.planned`, `transitions.clean` and `transitions.gap` exist only when a plan was made, so games without one keep their state hash; no existing golden moved. New goldens: spoke-b-90 `approach4-transition-plans` (two clean handoffs, the first identical to the hand termination it replaces) and `approach4-transition-gap` (a 25-day bridge, flagged day 36, five days down).

## Addendum, 2026-11-08 (M3-16): inherited arrangement fidelity
Scenario `inheritedArrangements[]` gain optional `quantity`, `dailyCostCents`, `obligatedCents` and `fundingLine`; `ucaState` (already in the schema, ignored until now) becomes a live `UcaState` with `PriorObligatedCents` (its `obligatedCents`) and optional `quotedTotalCents` (default: daily cost over the whole period). Prior obligations count toward the obligation caps, the 50% definitization trigger and the definitized price; `Arrangement.ObligatedCents` stays this game's. A missing `qualifyingProposalDay` is drawn from the "uca" stream at session creation (issue day plus the vendor's lag); a proposal day before day 1 means it is in hand. Mobilization is not charged for a row that started before day 1. Supply lines on an inherited row with a `quantity` are sized as for an award. Bundle checks: positive quantity, non-negative daily cost, start before end, a known funding line, an obligation only with a funding line, `ucaState` only on a `uca` row with obligations within a positive NTE, a proposal not before issue, and a funding line for an undefinitized UCA. Rows that set none of the new fields load exactly as before; no golden moved. Termination notice and claims (`noticeDays`) are M3-19.

## Addendum, 2026-11-08 (M3-18): vendor.reliabilityDrop and inherited contracts under administration
Event effect `vendor.reliabilityDrop` (target an inherited arrangement id, `value` a reliability 0..1) sets that arrangement's reliability to the lower of its current value and `value` from the event day; it never raises it, and does nothing to an arrangement that has ended. New predicates `arrangement.noCureNotice` and `arrangement.notReplaced` (targets inherited arrangement ids) read the performance-issue state: no cure notice delivered or in work on it; nothing created this game for its site and capability is `Active`. The bundle refuses a drop or one of these predicates whose target is not an inherited arrangement, and a drop value outside 0..1.
Inherited arrangements with written terms are now curable (`Curable` no longer requires `CreatedDay > 0`): their failures open performance issues, take `CureNoticeAction` and `DesignateCorAction`, and in a scenario with a COR roster are reported through the COR. Shipped scenarios inherit only host nation support, which has no written terms, so no golden moved.

## Addendum, 2026-11-08 (M3-19): termination notice and claims
`TerminateAction.WithNotice` (default false, so existing logs read the same) asks for the contract's notice: allowed only on an arrangement with `NoticeDays` (from an inherited row's `noticeDays`), refused otherwise. With notice, performance ends `NoticeDays` after the termination work completes. Without notice on such a contract, it ends at once and a `ClaimState` is filed (`Session.Claims`, `SessionView.Claims`) with a `Compliance` record and `WorkKind.ClaimSettlement` shop work; settling it adds the amount to the arrangement's incurred cost and obligates it from its line as far as the line allows. No claim when a performance issue on the arrangement ended in default. No metric was added (a new metric key would move every golden's state hash); the claim count and amount are in the scorecard.

## Addendum, 2026-11-08 (M2R-03): small buys and the purchase card program
Actions `holdSmallBuys { hold }` and `standUpGpcProgram` (additive). The customer small-buy stream is population math (rules `smallBuys`), worked from the hours the day's queued work leaves, so existing input logs keep their timing; a backlog builds on a busy or holding shop and the CE customer goes to the commander once about three days' worth are waiting (a confidence hit). The card program (rules `gpcProgram`) is a work item that takes only leftover hours, needs purchase card accounts, and afterward diverts 80% of the stream. `TopStripView` gains `SmallBuysToday`, `SmallBuyHoursToday`, `SmallBuyBacklog`, `SmallBuysHeld`, `GpcProgram`; `BoardLinkKind.SmallBuys` links the daily line; `SessionView.SmallBuysHeld/SmallBuyBacklog/GpcProgramDay/GpcAvailableDay`. Metrics `shop.smallBuys`, `shop.smallBuyHours`, `shop.smallBuysHeldDays`, `shop.gpcProgramDay`.

## Addendum, 2026-11-09 (M2R-04): going to people
Actions `findFinance`, `joinStaffMeeting { attend }`, `askSco { question }`, `meetVendor { vendor }` and `engageJ4 { id, site, capability, quantity, durationDays? }` (additive). Each is a `WorkKind.Visit` item with a rules shop-hour cost (`goingToPeople`); what the person says is a new `RecordKind.Visit` record whose subject is `person <id>` when a cast member said it, which `Link` maps to the new `BoardLinkKind.Person` (LinkId is the person id; `PersonFor` returns them). A weekly staff meeting is created before the day's shop work and goes to the front of the queue. SCO answers draw their lag from a new "people" stream, created only on first use; a scenario's new `tutorial` flag adds the rules `tutorialDirection` to an answer. `engageJ4` adds an `acsa` arrangement at no cost to the shop (no funding line), sharing the partner's stock with ACSA orders. A vendor meeting can bring a hidden undefinitized UCA to light (`RevealSource.Vendor`, alongside review and inquiry). Views: `SessionView.PreviewVisit`, `FinanceFoundDay`, `StaffMeeting` (`StaffMeetingView`), `ScoQuestions` (`ScoQuestionView`), `VendorConfidence`, `VendorMetDay`, `VendorReps`. No metric keys were added and no policy uses the actions, so every golden's state hash is unchanged.
